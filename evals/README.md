# 场景评测（evals）

给 `qa-design` 这类**输出由模型产生**的环节做评测。与 `tests/` 下的单测是两回事，
判据不能混用。

## 为什么要分成三类证据

`design.md` 的 Testing Strategy 里定了三类检查。这里最容易出错的是把第二类当成第三类：

| 类型 | 证明什么 | **不能**证明什么 |
|---|---|---|
| 确定性单测（`tests/`） | 脚本逻辑正确 | 模型输出好不好 |
| 结构检查（本目录 `structural`） | 格式合规：有 `covers`、预期不含模糊词、边界值齐 | **需求覆盖完整、预期正确** |
| 输出质量（本目录 `rubric`） | 按人工 rubric 评分的实际质量 | 可自动化、可回归 |

所以 `run_evals.py` 的报告把结构结果与质量结果**分列**，绝不合成一个总分。
只要有人把"结构检查 12/12 通过"写成"用例质量达标"，这套评测就失去意义。

## 目录

```
evals/
├── fixtures/          输入：需求 fixture（正例 + 反例）
├── rubrics/           评分表：逐条 checklist，标明是否需人工判断
├── runs/              输出：每次评测的结果（gitignored）
└── run_evals.py       跑结构检查 + 生成人工评分清单
```

## fixture 的两类

**正例**：有明确约束的需求，模型**应当**产出特定用例。可用结构检查自动判定。
例如数值范围 `[3, 32]` → 必须出现 min-1/min/max/max+1。

**反例**：看起来完整、实则不可验证的需求。模型**应当**标为阻塞项而不是硬造用例。
这类只能靠 rubric 判定 —— 结构检查看不出"这条用例是硬造的"。

反例比正例重要。正例测的是"会不会做"，反例测的是"会不会知道自己做不了"。

## 必须记录的元数据

每次评测都要记录模型与配置版本，否则结果无法归因：

```json
{
  "model": "<模型标识>",
  "agent_config_version": "<qa-design 配置的版本或哈希>",
  "prompt_version": "<提示词版本>",
  "run_at": "<UTC 时间>"
}
```

同一份 fixture 在不同模型/配置下的结果不可直接比较。

## 漏报与误报要分开统计

| 指标 | 含义 | 为什么单独看 |
|---|---|---|
| 漏报 | 反例未被标为阻塞项 | 直接导致缺陷流出，代价最高 |
| 误报 | 正例被误标为阻塞项 | 代价是人工复核成本，可接受但要可见 |

只报一个"准确率"会把这两者的代价差异抹平。

## 用法

```bash
python3 evals/run_evals.py --list                  # 列出 fixture 与对应 rubric
python3 evals/run_evals.py --fixture boundary-range --output path/to/cases.md
python3 evals/run_evals.py --report evals/runs/<id>/    # 汇总结构 + 人工评分
```

`run_evals.py` **不调用模型**。它只做两件事：对已产出的用例文件跑结构检查，
以及把 rubric 展开成待人工填写的清单。调用模型、收集输出由执行者完成 ——
这样评测脚本本身是确定性的、可单测的。
