# Task 3 第一步：执行进程边界定位（2026-09-21）

本文件回答 Task 3 的前置问题：**实际执行 agent 文件写入的是哪个进程边界，操作系统级隔离
能挂在哪里。** 结论只依据本文记录的外部可复核证据，不采信任何模型自述。

原始输出归档在 `results/`，探针脚本在本目录，可重跑。

---

## 1. 问题与判据

item 8 的事实是：同一份子代理配置**直接调用**时 `permissions.deny` 生效，被**委派调用**时
同一条 deny 未生效、写入成功。这说明应用层权限判定在委派路径上不可靠，但**不能**由此推出
"执行环境隔离无效"——操作系统隔离约束的是**发起写入的进程**，与该进程内部的权限判定是否
正确无关。

所以隔离方案设计前必须先确定：

- Q1：agent 的 shell 命令跑在哪个进程下（这条已在 item 5 中间接看到，本次补完整进程树）
- Q2：工具级 `fs_write`（不经 shell）是否由一个**per-agent 的独立进程**执行？
- Q3：**委派**给子代理执行写入时，是否创建了新的操作系统进程？

Q2/Q3 决定隔离粒度：若不存在 per-agent 的进程边界，就不存在"只沙箱化 `qa-executor`、
不影响 `qa-lead`"这个选项。

---

## 2. 已确认的事实

### 2.1 shell 命令的进程归属（Q1）

`results/kiro-process-tree.txt`：

- 交互 shell 祖先链 `4041 /bin/zsh → 4037 zsh (kiro-cli-term) → 3612 Kiro Helper → 3590 Kiro`
- 即：agent 执行的 shell 命令是 **Kiro Helper（Electron 工具进程）的后代进程**，
  在宿主机上以用户 `kk` 身份运行，没有任何额外隔离

**设计后果：** shell 起源的写入（item 5 那条路径）发生在**我们能控制的子进程**里，
因此容器/挂载级隔离对这条路径是可用的（podman 只读挂载已在上一轮验证为真实拦截）。

### 2.2 委派写入期间未记录到新建进程（Q2/Q3）

> **2026-09-21 表述更正。** 本节上一版写的是"IDE 内不存在 per-agent 的操作系统进程
> 边界"，并据此推出"委派链内部拆分不可能"。外部复核指出这超出证据，成立：
> 采样器只观察**进程创建**，不做写入到 PID 的归属；没有新进程仍可能由采样开始前
> 就存在的工作进程、进程池或常驻服务完成写入。因此本节结论收窄为
> **"本轮快照没有记录到 Kiro 树中新建进程"**，不再声称进程架构。
> 另外"顶层会话"也不自动意味着独立 OS 进程，原推论一并撤回。

方法：在宿主机上按固定间隔快照完整进程表，记录窗口内**新建**的进程（以 `pid + lstart`
配对识别，避免 PID 复用误判），窗口内分别执行 ①主代理直接 `fs_write` ②委派子代理
`fs_write`。采样器自身派生的 `/bin/ps` 子进程被显式排除并计数。

| 轮次 | 采样间隔 | 样本数 | 覆盖 | Kiro 进程树内新建进程 |
|---|---|---|---|---|
| 轮次 | 设定间隔 | 实测间隔 | 样本数 | 覆盖 | Kiro 树内新建进程 |
|---|---|---|---|---|---|
| pass 1 | 0.5s | 未记录 | 68（37.5s） | 直接写 + 委派写 | 1 个瞬时子进程 `pid=38202 ppid=3590 comm=(Kiro)`，仅出现在 1 个样本 |
| pass 2 | 0.1s | **约 150ms（事后由 148 次/22.1s 反推）** | 148（22.1s） | 委派写全程 | 0 个 |
| pass 3 | 0.1s | min 0.027 / p50 0.029 / **max 54.3s** | 866（86.5s） | 委派写全程 | 0 个（但间隔分布本身不可用，见下） |
| **pass 4** | 0.1s | **min 0.095 / p50 0.100 / max 0.105** | 248（24.7s） | 委派写全程 | 1 个 `sh`（ppid=3612），出现在探针自己执行 shell 命令的同一时刻，归因于测量自身 |

- pass 3 暴露了第一版"固定节拍"修法的缺陷：落后于节拍时会连续补采（p50 空转到 29ms），
  同时仍出现 54.3s 的长间隙。已改为**跳过错过的节拍**，pass 4 的实测分布才与设定值一致。
  pass 3 的数据保留在 `results/reduced-pass3-flawed-intervals/`，作为"必须公布 max 间隙"
  的实例证据——只看"866 次快照"会以为覆盖很密，实际中间有 54 秒什么都没看到。
- pass 4 详情：`results/delegated-write-pass4-fixed-tick.txt`；原始采样降采样归档在
  `results/reduced-pass4-fixed-tick/`（保留每次快照的 t/wall、Kiro 子树、整表 sha256，
  可逐间隙复核）

- pass 1 的 `(Kiro)` 瞬时子进程出现在 11:22:44，距委派开始已 25s，**pass 2 未复现**，
  且两次委派写入都成功；没有证据把它放进写入路径。原始数据：
  `results/delegated-write-pass1-0.5s.txt`、`results/delegated-write-pass2-0.1s.txt`

  `sleep`，与 Kiro 无父子关系

### 2.3 测量能力的标定（否定结论的适用范围）

"没看到新进程"只有在知道**多短的进程会被漏掉**时才有意义。

正对照（`results/control-4s-canary.txt`）：0.25s 间隔下，已知 PID 的 4 秒进程
被判定为 `CONTROL_PASS`。

> **2026-09-21 表述更正（外部复核指出三处，全部成立）：**
>
> 1. **"0.1s 间隔"是设定值，不是实测值。** 归档的 pass 2 是 148 次 / 22.1 秒，
>    相邻间隔实际约 **150ms**。原因是采样器当时"干完活再 `sleep(interval)`"，把
>    `ps` 调用与写盘时间叠加在间隔之外。已改为按固定节拍对齐，并让 `report`
>    强制打印实测间隔的 min/p50/p95/**max**；能漏掉多长的进程由 **max 间隙**决定。
> 2. **每种寿命只跑了一个样本。** 一次捕获不能保证后续必然捕获，"100ms 可检出"
>    当时不成立为下限结论。标定脚本已改为每种寿命重复 5 次并输出捕获率。
> 3. **原始 `samples.jsonl` / `meta.json` 未归档**（留在 /tmp 后被清理），
>    第三方无法逐间隙复核。已补 `proc_diff_probe.py archive` 模式，
>    连同 `raw-manifest.json` 哈希清单一起入库。

旧的单样本标定结果（保留作为历史记录，**不作为检测下限结论**）：
1000ms / 300ms / 100ms 各捕获一次，20ms 未出现在任何样本。

修正后的标定（`results/detection-floor-calibration-repeat5.txt`，每种寿命重复 5 次，
实测间隔 max 0.104s）：

| 金丝雀寿命 | 捕获率 |
|---|---|
| 1000ms | 5/5 |
| 300ms | 5/5 |
| 150ms | 5/5 |
| 100ms | 5/5 |
| **50ms** | **3/5（已证实会漏）** |
| **20ms** | **1/5** |

**因此 2.2 的否定结论应表述为：** 在 pass 4 的 248 次快照（实测相邻间隔 max 0.105s）中，
委派写入期间**没有记录到** Kiro 树中的新建进程（唯一的 `sh` 归因于探针自身的 shell 命令）；
50ms 量级的进程已证实会漏，短于 max 间隙的进程可能整段落在两次快照之间。
**并且**：即便没有任何新进程，也不能推出写入由哪个进程完成——采样器不做 PID 归属。

## 3. 一条被证伪的测量方法（保留记录）

初始方案是让 agent 写入一个 FIFO：写入方会阻塞在 `open()` 直到读端出现，期间用
`lsof <fifo>` 读出它的 PID。

该方法**不成立**，由对照组直接判死（`results/fifo-method-invalidated.txt`）：

- 控制写入方 PID 32944 确实在该 FIFO 上阻塞了约 90 秒——证据是读端挂上后
  `content.txt` 收到 `CONTROL-WRITER-PID-32944`
- 同期 **220 次 `lsof` 采样全部为空**

原因：进程阻塞在 `open()` 内部时**尚未建立文件描述符**，而 `lsof` 枚举的是已打开的
描述符。若当初没做对照组，只跑 agent 一侧，"抓不到写入方"会被误读成
"没有进程写入"或"写入走了 temp+rename"——这正是本项目反复出现的那类误判。

脚本保留在 `fifo_writer_probe.py`（含 `control` 模式），作为方法论反面样例，
不作为 Task 3 的证据来源。

## 4. 对隔离方案的直接约束

1. **尚未找到可供 per-agent 挂载的进程边界，但这不等于不存在。**（2026-09-21 收窄）
   本轮快照没有记录到委派写入期间的新建进程，因此**目前没有**可以用来"只沙箱化
   `qa-executor`"的观测到的进程对象。但这不是架构结论：写入可能由采样开始前就存在的
   常驻进程完成，其身份未归属。所以：
   - 不得据此宣称"委派链内部拆分不可能"；这条原推论**已撤回**
   - 不得据此宣称"顶层会话就是独立 OS 进程"；顶层会话与进程边界是两件事
   - 下一步要的是**正面归属证据**（`sudo fs_usage` 覆盖直接链路与委派链路、唯一
     canary、记录实际 open/write/rename 事件），而不是继续加密采样频率
2. **两条绕过路径要用两种不同手段处理：**
   - item 5（shell 起源写入）：容器/只读挂载可拦截，已验证原语有效，属可落地项
   - item 8（工具级委派写入）：发生在 IDE 宿主进程内，容器化该宿主进程在 macOS 上
     未能验证（`kiro-cli` 是 Mach-O universal 二进制，Linux 容器跑不了；`sandbox-exec`
     已弃用且 `-f` 行为不稳定）。**记"未能验证"，不记"不可行"**
3. **item 8 的可落地缓解是结构性的，且依据是已观测到的权限行为，不是进程架构推论：**
   同一份配置直接调用时 deny 生效、被委派调用时 deny 失效（item 8 三组对照）。
   因此"安全关键角色不经委派调用"这条临时措施成立——它的依据只有这一条观测，
   与进程边界无关。（原文把它挂在进程架构结论上，已更正。）
4. **CI 从可信产物重建门禁输入仍是独立防线**，但它在执行之后发生，防不住执行期间的破坏，
   不能替代第 2 条。

